# feature

> 使用方式：复制本文件到 `docs/design/` 下，重命名为 `<功能名>-design.md`，按提示逐节填写。
> 什么时候需要写：方案有多个可选路径 / 涉及数据模型或 API 变更 / 影响多个模块时。简单的只读小功能不必走此流程。
> 讨论原则：Agent 查事实，人做决策——本文档用于对齐方案，不是开工许可；评审通过后再进 TDD 红绿循环。

## status

`draft`（草案，讨论中）→ `reviewed`（评审通过，可开工）→ `implemented`（已落地，实测数据已回填）→ `superseded`（被后续设计取代，注明替代文档链接）

- **当前状态**：`draft`
- **评审人 / 评审日期**：（评审通过后回填）
- **关联 issue**：`.scratch/` 中的 issue 编号或链接

- **要解决的问题**：

## 验收标准

> 可实测、可判定的标准，禁止虚构数据；上线后回填实测值。安全相关变更需同步核对手册红线（只读接口/白名单优先）。

- [ ] （示例格式）降噪效果：xx 场景下重复告警减少 ≥ x%，0 漏报
- [ ] （示例格式）单次调查步数 ≤ 15 / 耗时 ≤ 5 分钟 / 成本 ≤ ¥0.5
- [ ] 单元测试覆盖约定接缝，全量测试通过
- [ ] 评测台回归通过（涉及 Agent 行为时必填）

## 依赖

> 明确上下游依赖，前置依赖未就绪时不要开工。

- **前置依赖**：（已有的模块 / 已合入的决策 / 环境）
- **数据 / 环境依赖**：（Prometheus 指标覆盖、日志关键错误、数据集等）
- **后续影响**：（此设计为哪些后续功能铺路）
