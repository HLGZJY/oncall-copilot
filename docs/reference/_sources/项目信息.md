## 2.1 运维基础层

| 术语                           | 含义                | 备注                       |
| ---------------------------- | ----------------- | ------------------------ |
| ⭐ **SLA / SLO / SLI**        | 服务等级协议 / 目标 / 指标  | SLO 例：99.9% 请求 < 200ms   |
| ⭐ **MTTR / MTTD / MTBF**     | 平均修复 / 发现 / 无故障时间 | AIOps 的核心 KPI            |
| **错误预算（Error Budget）**       | SLO 允许的失败额度       | 花完了就不能再发版（SRE 核心机制）      |
| **Incident（事故/事件）**          | 影响用户的异常           | 区别于 Alert（告警，只是信号）       |
| **P0/P1/P2/P3**              | 故障等级              | P0 = 全网挂了上热搜             |
| ⭐ **On-call（值班）**            | 轮班待命响应故障          | 本项目名字 OnCall Copilot 的由来 |
| **Runbook / SOP / Playbook** | 处置手册，标准操作步骤       | AIOps 里被解析成可执行工具         |
| **Postmortem / 复盘**          | 事故后的总结报告          | 强调**对事不对人**（blameless）   |
| ⭐ **变更（Change）**             | 任何对生产环境的修改        | **80% 故障来自变更**，排障必查      |
| **CMDB**                     | 配置管理数据库，记录资产与关系   | 拓扑关联的基础                  |
| **工单（Ticket）**               | ITSM 里的任务载体       | 智能提单、智能分派是 AIOps 落地点     |
| **灰度 / 金丝雀 / 回滚**            | 发布策略              | AIOps 做变更风险评估时要懂         |

## 2.3 数据与算法层

| 术语                      | 含义                  | 备注                                     |
| ----------------------- | ------------------- | -------------------------------------- |
| ⭐ **告警降噪 / 收敛 / 压缩**    | 把 N 条告警聚成 1 个事件     | AIOps 第一价值点                            |
| ⭐ **告警指纹（Fingerprint）** | 用规则+实例+时间窗算出的去重 key | 去重的第一道防线                               |

| ⭐ **时序异常检测**            | 从时间序列里找异常点/段        | 统计法（3σ/EMA）+ ML（IsolationForest）+ 深度学习 |
| **动态基线**                | 随时间/周期变化的正常范围       | 固定阈值误报的克星                              |
| **因果推断 / 因果图**          | 区分相关与因果             | PC 算法、因果森林等                            |
| **依赖图 / 拓扑**            | 服务之间的调用关系           | 基于拓扑的告警传播分析                            |
| **日志模板解析**              | 把非结构化日志变成"模板 + 参数"  | Drain、Spell 等算法                        |
| **知识图谱**                | 用图结构表达资产/故障/关系      | 白鳝用 Neo4j，PG 用 AGE 扩展                  |

# 第2部分 · 主流方法与生态

## 3.1 方法论演进：四代

| 代际                | 时间        | 核心方法                | 能做什么           | 做不到什么              |
| ----------------- | --------- | ------------------- | -------------- | ------------------ |
| **第 1 代：规则**      | 2010s     | 固定阈值、正则、专家规则        | 发现问题           | 误报多、无推理、规则爆炸       |
| **第 2 代：统计/ML**   | 2016–2022 | 时序异常检测、聚类、因果图       | 降噪、异常检测、辅助定位   | 需要大量标注、难泛化、无语义     |
| **第 3 代：大模型问答**   | 2023–2024 | RAG + 知识库问答         | 快问快答、解释告警、生成脚本 | **没有慢思考，解决不了复杂排障** |
| **第 4 代：Agentic** | 2025–现在   | 自主决策闭环 + 多智能体 + MCP | 深度取证、假设检验、证据链  | 成本高、延迟长、可控性挑战      |

OpenDerisk 的讲者把第 3 代到第 4 代的转折讲得很清楚：

> "今年之前，整个智能化的应用场景其实都是以**知识库类型的应用**为主……这些产品的特点是可以快速完成用户的响应，但他**没有慢思考、深度思考的能力**。"  
> "运维领域有非常多的复杂任务，比如说我们要做一个故障的排查……通过知识库类型的产品**快问快答的方式，显然是不能解决我们的问题**。"

## 3.2 智能运维成熟度分级（L0–L5）

这是白鳝（30 年数据库老兵，《数据库智能运维实战》作者）提出的框架，也是**全套素材里最实用的一把尺子**：

| 级别     | 名称        | 能力                                        | 典型形态                   |
| ------ | --------- | ----------------------------------------- | ---------------------- |
| **L0** | 人工运维      | 纯人工                                       | 人看 Grafana             |
| **L1** | 辅助分析      | 自动汇总、告警、**生成巡检报告**                        | 星海的集群健康巡检              |
| **L2** | 建议与人工执行   | **提出候选根因**、调用只读工具验证、形成处置建议，**人审核 + 手工执行** | DeepSeek 培训稿的告警处理建议    |
| **L3** | 受控自动执行    | 通过工具**自动执行 + 自动检查结果**                     | 你的 OnCall Copilot 目标水位 |
| **L4** | 限定场景自治    | 在预先批准的对象/时间/风险/工作范围内**自动闭环**              | 容量管理场景                 |
| **L5** | 跨域协同与动态自治 | 跨应用/数据库/网络/基础设施共享事实，**围绕业务目标自主规划**        | 仍受政策、风险、预算、审批约束        |

**三条关键补充**：

1. **L3 的安全机制必须是白名单，不能是黑名单**（白鳝原话）：
   > "黑名单机制我们做过很多尝试，现在 AI 的**越狱能力很强**，哪怕 Qwen 27B 这样的模型，它的越狱能力都很强——如果你用黑名单，他会尽可能去绕开黑名单。"
2. **硬件故障已经 L5，软件故障还在 L3 左右**（冯若航的判断）：高可用 failover 本身就是一种自动驾驶，"不需要人类干预，它自己可以完成"；但"你写 bug 了、删表了，这种自动驾驶是难做的"。
3. 各厂商有自己的分级（如嘉为蓝鲸 Lv.1 辅助建议 → Lv.4 Agent 自主），**面试或方案里讲清楚你用的是哪把尺子**。

## 3.3 核心技术模块拆解

### 模块 A：告警降噪与事件关联

**问题**：500 条告警 → 3 个事件，且 0 漏报真实故障。

**主流手段（四层递进）**：

| 层级    | 手段                                | 说明            |
| ----- | --------------------------------- | ------------- |
| 1. 去重 | **告警指纹**（规则 + 实例 + 时间窗）           | 完全相同的告警合并计数   |
| 2. 抑制 | 父子规则、维护窗口                         | 下游挂了，上游告警抑制   |
| 3. 聚合 | **时间相关性 + 拓扑关联 + 文本相似度**          | 一个故障引发的告警簇    |
| 4. 分类 | **规则预筛 + LLM 分类**（误报 / 风险 / 真实事件） | 不确定的落"风险"而非丢弃 |

**关键设计**：

- **规则先行、LLM 兜底**——便宜且确定性的部分交给规则，模糊地带交给模型（成本控制的核心）
- **0 漏报怎么保证**：宁可误报为"风险"也不丢弃；用"降噪率 + 漏报率"双指标，不能只看降噪率
- 你的项目目标：剧本集内降噪 ≥80%，**0 漏报**

### 模块 B：异常检测

| 方法                    | 原理                    | 优点            | 缺点         |
| --------------------- | --------------------- | ------------- | ---------- |
| 固定阈值                  | 人工设阈值                 | 简单可解释         | 误报/漏报都多    |
| 统计基线                  | 3σ、EMA、同比环比           | 能适配周期性        | 对多峰分布无能为力  |
| 孤立森林（IsolationForest） | 随机切分找易孤立点             | 无需标注、对高维有效    | 难解释、对时序不敏感 |
| 深度学习                  | LSTM/Transformer 预测残差 | 拟合复杂模式        | 需大量数据、黑盒   |
| **LLM 语义层**           | 理解日志深层含义              | **零样本识别未知错误** | 慢、贵、可能幻觉   |

**最佳实践**：不是二选一，而是**分层**——

> 统计/ML 负责"发现异常点"（快、便宜、确定），LLM 负责"解读这批异常意味着什么"（慢、贵、有语义）。


### 模块 C：根因定位（RCA）—— 皇冠上的明珠

**四条技术路线**：

| 路线                    | 代表                        | 思路                           | 局限                |
| --------------------- | ------------------------- | ---------------------------- | ----------------- |
| **1. 规则/专家系统**        | 早期 AIOps 产品               | 故障树、专家规则                     | 规则爆炸、覆盖不了新问题      |
| **2. 因果发现/依赖图**       | PC 算法、随机游走                | 从拓扑 + 指标相关性推因果               | 真实系统太复杂，假设难成立     |
| **3. 统计关联**           | 相关性分析、Granger             | 找同时异常的组件                     | **相关性 ≠ 因果**，这是死穴 |
| **4. LLM Agent 深度研究** | OpenDerisk、OnCall Copilot | **假设生成 → 取证验证 → 推翻/证实 → 迭代** | 慢（分钟级）、贵、需防绕圈     |

**第 4 条路线的关键结构（这也是你的项目要实现的）**：

```
          ┌─────────────── Agent 主循环 ───────────────┐
告警/问题 ─► Planner（下一步做什么） ──► Tool Registry（≥6 个工具）
          │        ▲                            │
          │        │                            ▼
          │   记忆（证据摘要）  ◄──── 执行工具（查指标/查日志/查变更/异常检测/查知识库）
          │        │
          │        ▼
          └── Verifier（证据支持假设？）──► 否 → 换假设 / 步数超限 → 求助人类
                   │ 是
                   ▼
            结论 + 证据链报告
```

**OpenDerisk 的实际跑法**（视频里看得最清楚）：

1. 问题路由到 `DevOpsAgent` 做规划
2. **规划 → 写代码 → 执行代码 → 看结果 → 再规划**（与 Code-Agent 交互极频繁）


3. 依次查：监控指标 → 容器指标 → 服务指标 → 全局阈值 → trace 调用链
4. 最后 ReportAgent 出一份带**关键证据链**的报告：基础数据对比、网络指标关联、调用特征、排除了哪些可能性、建议措施

**一个重要的工程洞察**：OpenDerisk 把"思考/规划"和"写代码"用**不同的模型**（推理模型做 plan，代码强的模型写代码）——这是**分层调用降成本**的典型实践。

### 模块 D：处置自动化与自愈

**这是 AIOps 最敏感的部分，也是最能体现工程成熟度的部分。**

**四道闸门**（缺一不可）：

```
① 干跑（Dry-run）  →  打印将要执行的命令 + 影响面
        ↓
② 人工确认门      →  人点 Confirm 才能继续（API 层拦截，不是靠提示词）
        ↓
③ 执行            →  在受控沙箱/指定容器内执行
        ↓
④ 恢复验证        →  自动回查指标，确认恢复；没恢复 → 回滚 or 转人工
```

**为什么必须用白名单**（三个真实教训）：

1. **冯若航（Pigsty 作者）的做法**：在 `CLAUDE.md` 里把操作分 5 级，**第 5 级（delete cluster / drop database / drop table）任何情况下禁止 AI 执行**，只能用户手动。
2. **提示词约束是无效的**：肖小聪的 cortex 项目，**GPT-5.6 把他的 AWS EC2 实例删了**。做操作系统的人给他的建议是——"写提示词都没用啊，他直接把 sudo 那个命令给换了"。
3. **SUSE 的做法**：AI 助手**不做任何删除动作**；创建/修改也会弹确认框。讲者说："这个'自动'肯定要打个引号……**谁也不敢放心去搞这个事情**。"

**一句话**：约束必须落在**系统层（API/权限/白名单）**，不能落在**提示词层**。

### 模块 E：知识沉淀（RAG 与知识图谱）

**标准流程**（星海在他的 Agent 里实现的完整链路）：

```
采集（官方文档 + 内部 Runbook + 历史工单 + 告警规则 + 人工补充）
   → 清洗（长度过滤、去重、结构化、规则化）
   → 切分 / 切词
   → 向量化（Embedding）
   → 入库（全量重建 + 增量更新 + 删除过期索引 + 命中率低的淘汰）
   → 监控（知识库自身的健康度）
```

**关键洞察**：知识库会"越来越聪明"的机制，是**增量更新 + 过期淘汰 + 命中率反馈**的闭环，而不只是往里塞数据。

**⚠️ 关于 RAG 的重大争议**（这是本批素材最有价值的部分，详见 4.4）：

- 反方（冯若航）：RAG 是上下文窗口只有几 K 时代的产物，现在窗口到 1M，它已从"架构范式"退化为"上下文工程工具箱里的一件小工具"
- 实证（白鳝）：在 BICQA 里让智能体自己选检索方式，**90% 以上它选全文检索，而不是向量**
- 建议：**不要神话 RAG，也不要抛弃它**——它是工具之一，不是架构本身

### 模块 F：评测（行业最稀缺的能力）

**为什么评测是差异化核心**：

- 没有评测，你的 AIOps 就是"演示级"而不是"生产级"
- 嘉为蓝鲸的选型建议里明确写："区分 AI 能力的真伪，可以看……是否在告警降噪、根因分析等具体场景有可验证的落地效果"

**一个可用的评测台长什么样**：

| 组成         | 说明                                  |
| ---------- | ----------------------------------- |
| **故障剧本库**  | ≥8 类，每类含注入脚本 + 触发告警 + 预标注根因/处置      |
| **Runner** | 全自动跑 N 遍，记录全过程                      |
| **指标矩阵**   | Top-1/Top-3 命中率、步数、耗时、LLM 成本、失败模式归类 |
| **模型对比**   | ≥2 个 LLM × ≥8 剧本                    |
| **回归**     | 每次代码变更跑一遍，防劣化                       |

**三个必须回答的问题**：

1. **评测集怎么保证不泄漏？** 训练/调优用的剧本与最终评测剧本要隔离
2. **Agent 结果怎么判对错？** 根因是字符串匹配还是语义匹配？需要人工仲裁还是 LLM-as-judge？
3. **失败模式怎么归类？** 是工具失败、是规划失败、还是幻觉？（这决定了你该改哪里）

## 3.6 2026 年行业现状：机会与警告

### 📈 机会侧

- **市场规模**：全球 AIOps 平台市场预计 2026 年达 **102–208 亿美元**（不同机构口径差异大），CAGR 18%–23%
- **渗透率**：全球 1000 人以上企业中，**56% 已部署或正在试点 AIOps**（2023 年仅 28%）
- **Gartner 预测**：到 2029 年，**70% 的企业将部署 Agentic AI 代理来运营 IT 基础设施**（2025 年不足 5%）
- **政策驱动**：国务院要求到 2026 年央企核心业务系统 AIOps 覆盖率不低于 85%
- **能力定名**：Gartner 2026 年把 AIOps 重新定义为 **Event Intelligence Solutions（事件智能）**，进入"启蒙上升期"

### ⚠️ 警告侧（这部分比机会更重要）

Gartner 2026 年 7 月发布的《AI in IT Operations 技术成熟度曲线》给出了三条**逆耳**的判断：

1. **工具不会先整合，反而会先膨胀**："AI 会整合你的工具"这个说法近期不成立，企业会积累"更多层、更多控制点、更多专门的可观测/编排/管理能力"，**短期是 console sprawl（控制台蔓延）而非 consolidation**
2. **事故风险将飙升**：**到 2028 年，40% 在生产中大规模运行 agentic AI 的 I\&O 组织，将遭遇业务关键性服务中断**（2026 年这一比例不足 1%）
3. **人工签核将大幅减少**：AI 建议动作的人类签核率从 2025 年的 **80% 降至 2029 年的 20%**，依赖的是"策略驱动的确定性护栏（deterministic guardrails）"而非人工审批

**这三条合起来意味着什么**：

> 未来 3 年是 AIOps 从"辅助工具"走向"自主执行"的关键窗口，但**风险会从"误报"变成"AI 自己搞出 P0"**。因此"护栏工程（guardrails）"和"Agentic AI Observability（观测 Agent 自身）"会成为最值钱的技能——Gartner 明确把 **Agentic AI Observability 列为 2–5 年内最该优先投入的技术**。

# 第3部分 · 核心难点与开放问题

> 这一部分是"为什么 AIOps 难"的答案，也是面试中最能体现深度的地方。

## 6.1 难点一：可观测数据的质量决定 AI 的上限

**这是全套素材里被反复验证的第一原理。**

三条独立佐证：

- **D6（SUSE）**：两个 AI 助手诊断能力差异巨大，根源是"**这两个产品本身，它的 MCP 所暴露出来的产品能力不同**"
- **D8（冯若航）**："**看一个厂商有没有自动驾驶能力，就看一个就行——你就看它监控系统做得怎么样**"；无好监控时 Codex "跑个 10 分钟都定位不到问题"，有大盘时"一分钟下钻定位"
- **Gartner 2026**：**超过 60% 的生产事故源于对已有数据的错误解读，而非缺乏可见性**

**推论**：

> 你的 Agent 调不好，先别怪模型——**先检查你的指标有没有覆盖这个故障模式、日志里有没有关键错误、拓扑关系是不是完整的**。

**实践检查清单**：

- [ ] 每一个故障剧本，是否至少有一个指标会出现可检测的异常？
- [ ] 关键错误是否出现在日志里（而不只是指标异常）？
- [ ] 是否有"K8s 健康但业务异常"这类剧本（考验业务语义层）？
- [ ] 服务依赖关系（拓扑/CMDB）是否可被 Agent 查询？

## 6.2 难点二：根因 ≠ 相关性

**为什么难**：

- 一个数据库慢查询 → 上游 5 个服务同时超时 → 指标上看 6 个组件都异常
- 统计关联只能告诉你"它们一起异常了"，不能告诉你"谁导致了谁"
- 真实系统的依赖图远比理论假设复杂（异步调用、重试、缓存、降级都会破坏因果链）

**四条路线的局限**（见 3.3 模块 C）：

- 因果发现算法（PC 等）依赖强假设，真实系统难成立
- 依赖图方法依赖拓扑准确性，拓扑一过时全错
- LLM Agent 路线不直接做因果推断，而是通过"**提出假设 → 取证验证 → 推翻/证实**"来**逼近**因果——这是目前最实用的路线

**关键设计**：

> 让你的 Agent 输出的不只是"根因是 X"，而是"**根因是 X，因为证据 A/B/C 支持它，而假设 Y 被证据 D 排除了**"。这就是证据链的价值——它把因果推断的责任部分交给了可验证的证据。

**评测上的对应**：Top-1/Top-3 命中率，**以及如何判对错**（字符串匹配？语义匹配？人工仲裁？LLM-as-judge？）。

## 6.3 难点三：自主性 vs 可控性

这是 AIOps 最尖锐的矛盾，也是**生产落地的第一拦路虎**。

**三道防线的有效性排序（从弱到强）**：

| 防线                   | 有效性     | 证据                                                              |
| -------------------- | ------- | --------------------------------------------------------------- |
| ❌ **提示词约束**          | **无效**  | D8：肖小聪的 AWS EC2 实例被 GPT-5.6 删掉；"写提示词都没用啊，**他直接把 sudo 那个命令给换了**" |
| 🟡 **人工确认门**         | 有效但会疲劳  | D6：SUSE 的做法；但 Gartner 预测签核率会从 80% 降到 20%                        |
| 🟢 **系统层白名单 / 只读接口** | **最有效** | D4："MCP 只暴露只读工具，**写操作从源头就不存在**——不需要靠二次确认去兜底"；D8：Pigsty 的五级操作分级  |

**白名单 vs 黑名单（D8 白鳝的原话）**：

> "黑名单机制我们做过很多尝试，现在 AI 的**越狱能力很强**，哪怕 Qwen 27B 这样的模型，它的越狱能力都很强——如果你用黑名单，他会尽可能去绕开黑名单，然后去做一些他想做的事。"

**可直接抄的设计清单（来自 D4）**：

1. 纳管用**一次性安装令牌**，之后改用**机器指纹令牌**（可吊销/限时/限次/轮换）
2. MCP **默认关闭**，未配置令牌时返回 404；启用后强制 16 位以上强令牌，支持作用域
3. **MCP 只暴露只读工具**
4. 工具调用**留痕 + 按令牌指纹限流**（60 次/分钟），超频自动记为安全事件
5. 远程命令：危险模式黑名单 + 命令段校验；**白名单敏感路径先规范化再拦截**
6. 审计日志 **HMAC 哈希链 + 双表镜像**
7. 数据送模型前**脱敏**；静态数据 AES-256-GCM 加密，**加密失败返回空值**

## 6.4 难点四：幻觉与证据链

**为什么幻觉在运维场景是致命的**：

- 通用问答里幻觉 = 说错一句话
- 运维里幻觉 = 删错一个库 / 重启错一个服务 / 耽误 30 分钟

**证据链是最有效的解药**。OpenDerisk 的立身之本就是这个：

> "我们在做诊断的过程当中，我们首先要回答清楚**它为什么是这个理由导致的**……你没办法去把底层的根因逻辑表达清楚、没办法把证据表达出来的时候，**你那个结果是不具可信的**。"

**证据链的数据结构（你的 M4）**：

```json
{
  "incident_id": "...",
  "steps": [
    {
      "step": 1,
      "thought": "用户报下单失败，先看订单服务的错误率和延迟",
      "tool": "query_metrics",
      "input": {"query": "rate(http_errors_total{svc='order'}[5m])"},
      "output_summary": "错误率从 0.1% 升到 12%，起始时间 14:32",
      "ts": "...",
      "tokens": 1240,
      "cost": 0.0031
    }
  ],
  "hypotheses": [
    {"text": "数据库性能瓶颈", "status": "confirmed", "supporting": [2,5,7], "against": []},
    {"text": "风控规则更新导致", "status": "rejected", "supporting": [], "against": [4]}
  ],
  "conclusion": "...",
  "confidence": 0.82
}
```

**三个必须做到**：

1. **每一步都能回溯到原始工具输出**（不能只存摘要）
2. **假设要有"证实/推翻"状态**，而不只是最终结论
3. **UI 上能一眼看懂**（时间线 + 证据节点）

## 6.5 难点五：评测——行业最稀缺的能力

**为什么难**：

| 难题         | 说明                                             |
| ---------- | ---------------------------------------------- |
| **黄金集从哪来** | 靠混沌注入 + 人工标注。8 类故障 × 3 次 = 24 次执行，成本不低         |
| **怎么判对错**  | "根因 = 数据库慢查询" 和 "根因 = 库存服务 DB 连接池耗尽" 算不算同一个答案？ |
| **防泄漏**    | 如果你用同一批剧本反复调 prompt，命中率高是"调出来"的还是"真会"？         |
| **失败模式归类** | 工具失败？规划失败？幻觉？超时？——决定了你该改哪里                     |
| **回归**     | 每次代码变更都要重跑，否则你不知道是变好了还是变坏了                     |

**一个可执行的方案**：

- **评测集分两组**：开发集（调 prompt 用）+ 保留集（最终报告用，调参时不许看）
- **判对错用两级**：先规则匹配（根因组件 + 故障类型），匹配不上再 LLM-as-judge（并人工抽检 20% 校验 judge 本身）
- **失败模式强制归类**：每步打标签（tool_error / plan_error / timeout / hallucination / no_signal）
- **每次 commit 跑回归**，把结果矩阵挂在 README

## 6.6 难点六：成本（Token 经济学）

**为什么重要**：Gartner 说 60% 的事故来自"看不懂数据"，但如果"看懂"一次要花 ¥5，这个项目就不可行。

**四条降本杠杆（按有效性排序）**：

| 杠杆                   | 效果                                                          | 来源           |
| -------------------- | ----------------------------------------------------------- | ------------ |
| 🥇 **优化 plan（意图识别）** | "**你 plan 得不好，每次你再节约，它还是会给你出一个长长的账单**"                      | 白鳝（D8）       |
| 🥈 **规则先行、LLM 兜底**   | 确定性部分不给模型                                                   | 通用实践         |
| 🥉 **缓存 + 分层调用**     | BICQA 缓存命中率 **89%**；简单问题走小模型（D1 的智能路由），思考用推理模型、写代码用代码模型（D7） | D8 / D1 / D7 |
| 4️⃣ **减少异构系统**       | "一个 PG 变成 PG 加另外两个数据库，**token 消耗量差不多有 6～7 倍**"              | 尹海文（D8）      |

**反面教训（很有启发）**：

> 白鳝发现用 LLM 切词更准确，但**额外增加 20 秒延迟，这个不能接受**——"每一次工具调用去搜索知识都要增加 20 秒"，于是**把大模型预切词功能下线了**。

**这告诉我们**：优化不能只看质量，要看**质量 × 延迟 × 成本**的综合。

## 6.7 难点七：安全——AI 自身成了新的攻击面

**D4 的核心洞察**：

> "一套成熟的运维平台，天然握着你所有服务器的 root 权限，**拿下他就等于拿下整个机房**。所以真正的问题是**他自己守不守得住**。"

**三层防护**：

1. **平台自身**（防被攻破）：CSP、PBKDF2 60 万轮、双引擎 Web 扫描、TLS 检查、登录限次
2. **AI 通道**（防被滥用）：MCP 默认关闭、只读工具、令牌作用域、限流、调用留痕
3. **数据**（防泄露）：静态加密、传输 TLS、**送模型前脱敏**、审计哈希链

**当前业界的真实短板**：D6 的讲者坦诚承认——"**目前我们没办法做脱敏**"，建议"大模型部署到本地，用私有的大模型"。

**这是你的项目可以强调的差异化点**：在 README 里明确写清楚脱敏策略，是很大的加分。

## 6.8 难点八：从"组件健康"到"业务异常"

**这是 AIOps 相对于传统监控的真正增量价值所在。**

D6 的 Demo 2 是最佳案例：

> Pod 全部 Running，K8s 层面"我这边是没有问题的"，但购物车 100% 不可用。根因是 cart 用的 **0.4.8 版 MongoDB 驱动已被废弃**，使用 OP_QUERY 协议，而后端 MongoDB 6.0 已移除该协议支持。

**这类问题的特征**：

- 基础设施指标全部正常
- 需要**跨层关联**（应用代码/驱动版本 + 后端数据库版本 + 错误日志语义）
- 传统可观测完全无能为力

**对你的项目**：你的 8 类故障剧本里，**至少要有一类是这样的"业务语义层"故障**（比如"版本不匹配导致的协议不兼容"），否则你证明不了 AIOps 相对传统监控的增量价值。

## 6.9 难点九：组织与落地——没有数字化就没有智能化

**最扎心的两句**：

> 白鳝："从我接触的有些客户来讲，**甚至有些客户他还处于原始社会**……数据库挂了好长时间他都不知道，还是网隔离的。"

> 肖小聪："企业 AI 转型的前置条件是——**你数字化了没有？你都还处在 Excel 小本本记东西的阶段，搞什么 AI 转型？**"

**落地曲线**：`数字化 → 可观测 → 自动化 → 智能化`，**跳步必然失败**。

**白鳝的深层洞察**：

> "**没有数字化，就没有智能化。** 而且现在我发现，**最难数字化的是人的能力和经验**。这些如果都能数字化了，那 AIOps 它会越来越靠谱。"

**以及一个反直觉的制度观察**：

> "**我有可能我们的 IT 政策，可能是限制我们智能化发展的一个条条框框。**"
